Rules a new agent must keep:

  • Never invent field values. A salary, deadline or employer that wasn't printed stays null.
  • Nothing is published without a human reviewer.
  • Re-running ingestion must never create duplicate rows. Row IDs are deterministic.
  • Never bypass the publisher's access controls. The worker stops on HTTP 401 or 403.
  • The Appwrite API key exists only on the server: in GitHub Secrets and worker/.env, never in the browser.

What the product does

Paper2Career turns newspaper recruitment classifieds into a searchable job feed. Every listing links back to the page it was printed on, and the feed records when the ad first and last appeared.

It solves four problems from the SRS:

ID Problem How Paper2Career answers it
P1 Vacancies are buried in dense classified pages OCR + extraction into fields that can be searched by role, location and qualification
P2 The same ad repeats; revised ads change details Matching across editions; changed fields become revisions for a reviewer
P3 Readers can't see where a listing came from Each listing shows the scanned ad, newspaper, date, page and a link to the e-paper
P4 Collecting ads by hand every day doesn't scale Scheduled worker runs three times a day; every run is logged

Users: job seekers (public feed), reviewers (who correct and publish extracted jobs), and the operator (who watches ingestion status).

MVP scope: one source, the English O Heraldo e-paper (epaper.heraldgoa.in), and its classifieds page. Out of scope for now: notifications to job seekers (FR-12), other newspapers, and employer verification.

Hackathon context: Appwrite Databases Hackathon, 19–31 October 2026. Appwrite TablesDB must be the core data store.

End-to-end flow

Each day the worker turns the newspaper's classifieds page into private job rows. A reviewer then checks each one against the scanned ad and publishes it to the public feed.

The worker writes only through the server API key. The website reads public rows anonymously, and reviewers act through their own Appwrite session. A run that finds no new edition is logged as NO_NEW_EDITION, and the 10:00 and 14:00 retries pick up a late edition.

Worker technical implementation

The worker is deterministic: the same page always produces the same row IDs. That property is what makes retries and re-runs safe.

Source adapter (source.py)

  • HeraldoSource.find_edition(day) fetches /epaper/oheraldo/DD-MM-YYYY. A 404 means the edition isn't published yet, and the method returns None.
  • parse_edition_html() selects a.pagethumb[data-ed_date=<ISO date>][data-page]. Each image src matches /uploads/epaper/YYYY-MM/(thumbnail-NNN-)?<hash>.jpg; dropping the prefix gives the full-resolution page.
  • If the site serves thumbnails for a different date, it returns None.
  • If no thumbnails are found at all, it raises LayoutChanged.
  • download_page() saves to downloads/<edition_key>/page-NN.jpg and computes a SHA-256 checksum. An existing file is reused.
  • HTTP etiquette: user agent Paper2Career/0.1 (+newspaper job discovery; respects robots.txt), 1.5 s between requests, 30 s timeout. A 401 or 403 raises SourceUnavailable. There is no retry with a disguised client.

OCR (ocr.py)

  • available_engine() honours OCR_ENGINE. Otherwise it uses Tesseract if the binary is found, then RapidOCR, then (on Windows) the built-in Windows 10/11 OCR through worker/scripts/winocr.ps1. The Windows engine reads a full 4189×6485 page in about 5 s, including the reverse-printed headings.
  • Tesseract: image_to_data(--psm 3) words are grouped into lines by (block, paragraph, line), with confidence scaled to 0..1.
  • RapidOCR: the page is processed in 1400 px tiles with 160 px overlap, so small classified print isn't downscaled away. A line touching an inner tile edge is dropped, because the neighbouring tile sees it whole. Overlapping duplicates are removed by IoU > 0.5.
  • PDF: native text lines via PyMuPDF. If the page has fewer than 200 characters of text, it is rendered at 300 dpi and OCR'd.
  • pipeline.page_lines() caches OCR output next to the image as page-NN.<checksum12>.ocr.json.

Finding the classifieds page

The e-paper has no section metadata, and the classifieds page moves (it was page 8 on 23 Oct 2026). looks_like_classifieds() OCRs each page's 800 px preview (about 350 KB, upscaled 2×) and needs at least 3 matches of: classified(s), situations vacant, wanted, vacancy, recruitment, appointment(s), walk-in. Only matching pages are downloaded at full resolution (about 6 MB each), so an edition costs about 13 MB instead of about 50 MB.

Segmentation (extract.segment_ads)

  1. Columns. split_columns() builds an x-coverage histogram of OCR line boxes. Gutters are x ranges whose coverage is at most 10% of the maximum (a headline spanning two columns still crosses a gutter). Line fragments on the same baseline are merged, because Windows OCR splits justified lines. Each line goes to the column holding its centre, which keeps right-aligned reference numbers in their own column.
  2. Headings. match_heading() accepts a short (at most 4 words), mostly uppercase line that names a known section. Known sections fall into three lists: JOB_SECTIONS (e.g. SITUATIONS VACANT), OTHER_SECTIONS (e.g. PROPERTIES WANTED, ACC WANTED, VEHICLES AVAILABLE, MATRIMONIALS) and NEUTRAL_SECTIONS (GENERAL, SERVICES, CLASSIFIEDS). A heading applies until the next heading, across columns.
  3. Reference mode. This applies when the page has at least 3 lines matching ^\W*(20\d{8})(?:\s*-\s*\d{1,2})?\W*$. O Heraldo prints a 10-digit booking number at the end of every ad. An ad ends at that number, which becomes ad_reference, and it may continue from the bottom of one column to the top of the next. Only a gap of more than 1.8× the line height breaks an ad that has no number yet; such a chunk has terminated=False.
  4. Gap mode (other layouts): a new ad starts at a gap of more than 0.9× the line height, or at a line opening with Wanted / Required / Urgently / Vacancy / Hiring / Walk-in.
  5. _make_ad() joins hyphenated line breaks. For an ad split across columns, the bounding box (used for the evidence crop) is the larger part.

Recruitment filter (recruitment_score, is_recruitment)

Score = 0.5 + 0.12 × (job keywords + role words) − 0.2 × non-job keywords. Then +0.3 inside a job section, or −0.45 inside an other section.

  • Accept a terminated ad in a job section if it has at least one job signal and a score of 0.5 or more.
  • Accept anything else only if the score is 0.75 or more and a known role word appears. This catches a "WANTED Driver" ad under GENERAL, and rejects a news article that sits among the ads.

Field extraction (extract_jobs)

  • One JobDraft per distinct role word in the ad, so "Driver and Cook" gives two jobs.
  • Fields are matched by regex against curated vocabularies:
  • ROLE_WORDS: about 110 roles
  • GOA_PLACES: about 60 towns
  • qualifications: SSC, HSSC, B.Com, ITI, GNM, Tally, …
  • experience
  • salary (Rs/INR/₹, "negotiable")
  • Indian mobile numbers and Goa landlines (0832)
  • emails
  • employer suffixes (Pvt Ltd, Hotel, School, …)
  • Deadline only after a cue such as "last date", "apply before", "by" or "walk-in on", parsed day-first. A date with no year rolls forward past the publication date. Anything outside ±1 year is rejected.
  • Confidence = 0.45 × OCR confidence + 0.35 × field completeness + 0.2 × recruitment score. Missing fields are listed in uncertain_fields (title, contact, ocr_text, multi_role_split).

Matching (matching.find_match)

Order Signal Result
1 Same content_hash (SHA-256 of the normalised ad text) and same role_index exact: linked automatically
2 fuzz.ratio(text) ≥ 93 and token_sort_ratio(title) ≥ 85 repeat: linked automatically
3 Title ≥ 85 and one of: a shared phone or email; text ≥ 80 with no conflicting contacts; text ≥ 97 even with different contacts probable: linked, revision for review
— None of the above new job

Candidates are jobs whose last_seen_at is within 90 days. changed_fields() compares deadline, salary_text, contact_phones, contact_emails, location, qualification, experience and employer. A field missing from the newer ad is not a change. Any change creates a job_revisions row and sets has_pending_revision. The job's own values stay as they were until a reviewer accepts.

Two rules came from the real-page run. First, use plain character similarity, never token_set_ratio, which scores 100 whenever one ad's words are a subset of another's. On 22 Oct that linked a liquor-store ad to a restaurant ad, and the newspaper's disclaimer to a chef ad. Second, when both ads print contacts and none overlap, they are different advertisers unless the text is near-identical, as with two "house help cum nanny" ads in different towns. A repeat "auto" match also requires no conflicting contacts. When a repeat supplies a value the job lacked, filled_fields() fills it in without a review.

Pipeline (pipeline.Ingestor)

  • run(days, trigger, pages, force) creates an ingestion_runs row with status RUNNING. It processes the last LOOKBACK_DAYS (default 3, IST), oldest first, then writes counts and a final status: SUCCESS, NO_NEW_EDITION, PARTIAL or FAILED. Every exception is captured into error_message. The CLI exits with 1 only on FAILED.
  • process_edition() skips an edition already PROCESSED or NO_RECRUITMENT_FOUND unless force is set. A crash leaves it PROCESSING, so the next run retries it.
  • store_job() works with deterministic IDs (each at most 36 characters, as Appwrite requires):
  • appearance = ap_ + sha256(edition_key|content_hash|role_index)[:32]
  • job = job_ + same
  • crop = cr_ + sha256(edition_key|content_hash)[:32]
  • revision = rv_ + appearance hash
  • If the appearance already exists, it does nothing (skipped_existing).
  • New jobs are always created needs_review and private. Low confidence (below REVIEW_CONFIDENCE_THRESHOLD, 0.75) adds a low_confidence flag.
  • Evidence crop: the ad's bounding box plus 18 px padding, at most 900 px wide, JPEG quality 82. It is saved through repo.save_crop(). A failure here is logged and doesn't fail the job.
  • import_file() is the manual path for a downloaded PDF or JPG with a known date and page.

Data model (Appwrite)

Database paper2career_db holds five tables, one storage bucket and one team. All of them are defined in setup_appwrite.SCHEMA and created idempotently. Strings longer than 2,000 characters are text columns, which keeps rows under MariaDB's 64 KB row limit. Shorter strings are varchar.

Storage

Permission model

Who Can
Worker (server API key) Everything; bypasses permissions
team:reviewers (table level) Read and update all five tables; read all crops
Anyone (read("any"), row level) Only jobs a reviewer has published, plus those jobs' appearances and crops; all ingestion_runs
Anyone No create, update or delete anywhere

Publishing adds read("any") to the job row, every appearance row of that job, and every crop file. Rejecting removes it. New appearances of an already-public job inherit public read when the worker creates them.

Frontend

The site is a single-page React app with four hash routes. vite.config.js sets base: './', so dist/ can be served from any path.

#/ Feed.jsx public Published jobs. Search covers title, employer, location, qualification, experience and the full ad text. Filters: location, deadline (any / not yet passed / has a deadline). Deadline wording comes from listingStatus() in format.js. The site never claims that a vacancy is open or closed.

Accessibility: semantic landmarks, labelled form controls, visible focus rings, aria-live on the result count, controls at least 40 px tall, and a responsive layout down to phone width.

Setup and deployment runbook

Going live takes four steps in this order: Appwrite, the first manual run, GitHub Actions, then the website. Steps marked (owner) need the project owner's accounts.

1. Appwrite project (owner)

  1. On Appwrite Cloud, create the project Paper2Career. Note the endpoint (e.g. https://fra.cloud.appwrite.io/v1) and the project ID.
  2. Create a server API key with these scopes: databases.read/write, tables.read/write, columns.read/write, indexes.read/write, rows.read/write, buckets.read/write, files.read/write, teams.read/write.
  3. Under Auth, enable Email/Password. Add a Web platform for each site hostname, including localhost.
  4. In worker/:
py -3.12 -m venv .venv
.venv\Scripts\activate
pip install -r requirements.txt
copy .env.example .env
python -m paper2career setup

Fill in .env before running setup.

  1. Under Auth, create each reviewer's user, then add them to the team reviewers.

2. First real ingestion

python -m paper2career run --date 2026-10-23 --page 8 -v

Page 8 was the classifieds page on that date. Open the review screen and check the extracted jobs against the scanned ads before publishing.

3. Daily automation (owner)

  1. Run git init in paper2career/, then push to a GitHub repository.
  2. Under Settings → Secrets and variables → Actions, add APPWRITE_ENDPOINT, APPWRITE_PROJECT_ID and APPWRITE_API_KEY.
  3. Under Actions → Paper2Career daily ingestion → Run workflow, run it once by hand. Optional inputs: date and a comma-separated pages list.
  4. The schedule then runs at 07:00, 10:00 and 14:00 IST. Downloaded pages and OCR results are cached between runs (actions/cache), so retries are cheap. GitHub can delay cron jobs by minutes.

4. Website (owner)

  1. Create frontend/.env.local with VITE_APPWRITE_ENDPOINT, VITE_APPWRITE_PROJECT_ID and VITE_APPWRITE_DATABASE_ID=paper2career_db.
  2. Test locally with npm install then npm run dev. Build with npm run build, which writes dist/.
  3. Host it on Appwrite Sites, connected to the repository: root frontend, build command npm run build, output dist, with the same VITE_* variables. Then add that hostname as an Appwrite Web platform.

End-to-end verification

The full pipeline ran automatically on two live O Heraldo editions (22 and 23 Oct 2026) on 23 Oct 2026. It found the right pages, stored 227 jobs and linked 124 of them across both days, using the local JSON store and Windows OCR. Bugs found and fixed during the run

  1. Column gutters were missed because a headline crossed them. The threshold was raised from 4% to 10%.
  2. Reverse-printed headings were misread ("SITUATIONS VAUNT"). Fuzzy matching now applies to lines larger than body text.
  3. A bare "WANTED" display banner switched the section. It is now ignored in numbered layouts.
  4. "will be provided" was read as a B.E. degree. B.A., M.A. and B.E. now count only in capitals.
  5. Booking numbers with a suffix (2026030842-1) merged two ads.
  6. token_set_ratio linked unrelated ads. Replaced by ratio plus the contact-conflict rule.
  7. A field that was previously unreadable created a review item. It now fills the gap silently.
  8. Large image downloads dropped. Up to 3 retries with backoff were added.
  9. Detection downloaded every full page (about 50 MB). It now screens 800 px previews, about 13 MB per edition.
  10. On news pages, an APPOINTMENTS heading pulled news stories into jobs. Headings are now limited to their column there, and news datelines are rejected.
  11. The CLI's --local swallowed the command name. It is now split into --local and --local-db PATH.
